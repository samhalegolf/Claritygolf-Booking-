Yes. The code research makes the boundary punch list much more concrete. There are a few places where the agent should change the architecture rather than simply add account_id filters.
The most important discoveries are that the current workspace resolver always returns the default account, an unmatched authenticated admin can fall through to the default admin user, calendar shell reads are unscoped before filtering, and several “legacy compatibility” paths deliberately retry without account_id. Those are exactly the behaviours we want gone before creating the clean second business.
Here’s the coding-agent version I’d use.
Clarity Booking — Business Account Boundary / Multi-Tenant Isolation Pass
Goal
Prepare Clarity Booking so we can create a second real Business Owner account using Supabase Auth and use it as an isolation test.
The objective is not yet to build a polished public signup/onboarding flow.
The objective is to establish a hard production boundary:
Authenticated user
        ↓
account membership
        ↓
authoritative account_id
        ↓
all account-owned reads/writes
A user from Business B must never:
	•	see Business A people;
	•	see Business A calendar items;
	•	inherit Business A settings;
	•	see Business A services/prices;
	•	access Business A integrations;
	•	write records into Business A;
	•	fall back to Business A if account resolution fails.
The existing production workspace must continue to work.
Treat this as a boundary/security migration, not general refactoring.
